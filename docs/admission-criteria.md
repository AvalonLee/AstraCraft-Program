# 收录标准

一句话概括：**协议要干净、文档要能读、你要真的用过。**

---

## 硬性门槛（H）

五条全过才能收。PR 模板里逐条勾选，`meta.yml` 的 `admission.checked` 字段记录
实际验证过的项。

### H1 可获取

- 公开可访问的仓库或主页
- 不接受：私有仓库、需付费才能看的内容、纯镜像仓库（收原仓库）
- 上游已删库的不收；收录后删库的按移除机制处理

### H2 协议明确

- 上游根目录有 `LICENSE` / `COPYING` 文件
- 能归一化成 SPDX 标识符
- **与 `SKILL.md` frontmatter 的 `license` 字段不冲突**

不满足 → 按 🔴 红灯做 link-only 存根，而不是拒收。
详见 [许可证政策](license-policy.md)。

**这条不可破例。**

### H3 文档可用

**skill 类**（`kind: skill` / `skill-collection`）：

- 有 `SKILL.md`
- `name` 字段与其所在目录名一致
- `description` 写清了「做什么 + 何时用」，而不只是一句功能名词

**项目类**（`kind: mcp-server` / `cli-tool` / `framework`）：

- 有 README
- 包含安装步骤
- 包含**最小可运行示例**——只有 API 列表、没有一个完整例子的不收

**这条不可破例。** 一个没法让人上手的项目，收进来只是增加噪音。

### H4 活跃度

- 最近一次提交 ≤ **12 个月**
- 未被 archived

**唯一可破例的门槛。** 见下文破例机制。

### H5 真实可用（分级要求）

| `admission.tier` | 要求 |
|---|---|
| `core` | **必须**本人跑通，且 `NOTES.zh-CN.md` 有真实评测内容（CI 强制校验非空且不等于模板原文） |
| `standard` | 建议跑通，笔记可后补 |
| `watch` | 可仅做资料性收录，须在笔记中说明未实测 |

这条是本仓库的立身之本。没有实测笔记的收录库，和一份书签导出没有区别。

## 为什么 star 不是硬门槛

这是一个刻意的设计选择。

用 star 卡门槛的问题在于：**star 是滞后指标**。一个刚发布两周的优秀 skill 可能只有
30 个 star，而一个三年前写的、早已不能用的项目可能有 5000 个。按 star 筛选，
筛出来的是"已经出名的东西"——那些用搜索引擎就能找到，不需要一个精选库。

本仓库的价值主张是**筛选和实测**，不是**统计和排名**。所以：

- star 作为 **S1 加分项**参与 `tier` 评级
- star 作为 **INDEX 的一个排序维度**
- star **不参与准入判断**

同理，fork 数、下载量、贡献者数量都不设门槛。

---

## 加分项（S）

满足 **≥3 项**可评 `admission.tier: core`。

| 编号 | 加分项 | 判定依据 |
|---|---|---|
| S1 | star ≥ 500 | `metrics.stars` |
| S2 | 近 3 个月有提交 | `metrics.pushed_at` |
| S3 | 有工程化结构 | 存在 `scripts/` / `tests/` / CI 配置 |
| S4 | 中文友好 | 有中文文档，或对中文输入输出处理得当 |
| S5 | 多 Agent 分发 | 有 `.claude-plugin/` / `.codex-plugin/` 等 manifest |
| S6 | 可复现示例 | 提供 demo、示例项目或录屏 |
| S7 | 版本管理规范 | 有语义化版本号 + CHANGELOG |
| S8 | 维护者响应积极 | Issue 平均响应 ≤ 1 周（人工判断） |

## 评级说明

| 评级 | 含义 | 在 INDEX 中 | 笔记要求 |
|---|---|---|---|
| `core` | 主推。经过实测，明确推荐 | 进入 README「精选条目」Top 10 候选 | 必须 |
| `standard` | 常规收录。可用，但不特别突出 | 正常列出 | 建议 |
| `watch` | 观察期。存疑、待验证、或已归档但有史料价值 | 标注 ⚠️ | 须说明未实测 |

`watch` 的典型用途：上游刚发布还看不出维护意愿、或者项目已归档但其设计思路值得
参考（比如某个已停更但定义了事实标准的规范）。

## 破例机制（Curator's Pick ★）

**只有 H4（活跃度）可以破例。** H1/H2/H3 是法律与可用性底线，H5 是仓库存在的理由，
都不可破。

破例操作：

```yaml
admission:
  tier: watch
  checked: [H1, H2, H3, H5]        # 不含 H4
  exception: "2024 年后无提交，但该规范已成为事实标准，后续项目均以其为准，具备参考价值"
```

`exception` 非空时，INDEX 会在该条目标 ★ 并展示破例理由。

**配额限制**：破例条目占总数比例 ≤ **15%**。超出时 `validate.py` 输出告警
（不中断构建，但会在 CI 摘要里显示）。这条限制的意义是防止破例从"例外"退化为
"惯例"——一旦超过 15%，说明标准本身需要重新讨论，而不是继续破例。

## 移除机制

触发条件（任一即触发）：

| 条件 | 判定 |
|---|---|
| 链接失效 | 每周 lychee 全量检查**连续两次**失败 |
| 上游删库 | GitHub 404 |
| 协议变更为红灯 | 同步时发现 LICENSE 改为 GPL/BUSL/SSPL 等 |
| 发现安全问题 | 上游被注入恶意代码、依赖存在未修复的高危漏洞 |
| 长期无法使用 | 依赖的上游服务下线、API 废弃导致功能完全不可用 |

处理流程：

1. 删除 `src/`（若有），移除 `.gitignore` 白名单
2. 协议变红灯的 → 降级为 link-only 存根（保留条目）
3. 其余情况 → 条目目录保留为纯说明存根**一个月**，之后清理
4. `CHANGELOG.md` 记入「移除」，写明 id、原上游地址、日期、原因
5. 更新 `THIRD_PARTY_NOTICES.md`

**为什么保留移除记录**：避免同一个已被排除的项目被反复提交收录。
`validate.py` 会检查新增条目的 `repo` 是否出现在 CHANGELOG 的已移除名单中。

## 收录 Checklist（PR 用）

复制到 PR 描述里逐条勾选：

```markdown
### 协议核查
- [ ] 上游有 LICENSE 文件，已确认 SPDX 标识符：______
- [ ] 已交叉核对 SKILL.md frontmatter 的 license 字段，与 LICENSE 一致
- [ ] 已检查子目录有无独立协议的资源（字体/图标/数据集）
- [ ] license_tier 判定为：🟢A / 🟡B / 🔴C
- [ ] copyright_holder 从 LICENSE 文件原文抄录，非猜测

### 硬门槛
- [ ] H1 公开可访问
- [ ] H2 协议明确
- [ ] H3 文档可用（有安装步骤 + 最小可运行示例）
- [ ] H4 最近提交 ≤ 12 个月且未归档　（破例请说明：______）
- [ ] H5 本人已实际跑通

### 文件完整性
- [ ] meta.yml 已填完，id 等于目录名
- [ ] README.zh-CN.md 七段式完整，非模板原文
- [ ] NOTES.zh-CN.md 有真实内容（core 级必须）
- [ ] vendored：src/ 内保留了上游 LICENSE，且**零修改**
- [ ] vendored：已在根 .gitignore 添加白名单例外
- [ ] link-only：目录下**没有** src/，已写 GET-IT.md
- [ ] 已更新 THIRD_PARTY_NOTICES.md
- [ ] 已更新 CHANGELOG.md

### 本地校验
- [ ] python scripts/validate.py 通过
- [ ] python scripts/gen_index.py 已重新生成，INDEX.md 已一并提交
```
